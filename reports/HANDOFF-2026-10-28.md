## 3. 生产用 Prompt

### 3.1 主提示词（已存在，直接用）

完整版在 `data-pipeline/species_deep/GENERATION-PROMPT.md`。用法：整段交给执行的 agent，把 `{{SPECIES_LIST}}` 换成本批物种（≤10 个）。它覆盖：
- 第 0 步：主关键词、美国月搜、KGR（allintitle ÷ 月搜）、SERP 前 10 名判断，不合格的剔除，记进 `reports/species-new-batch-<日期>.csv`
- 第 1 步：站内查重（`/species/`、`/guides/`、`/compatibility/`、`/fish-health/`、`/calculators/`），一个关键词一个页面
- 第 2 步：FishBase + Seriously Fish + 1–2 个交叉来源，≥4 条引用，图片只用许可明确的
- 第 3 步：按 `archer-fish.json` 的字段写；title 25–60 字符不用冒号，description 120–160 字符带数字，intro 首段含主词，主词密度 ≤3%，正文 1,200–2,000 词，8-gram 重复度 ≤5%
- 第 4 步：树形内链（首页 → Encyclopedia → 物种），`related` 优先同一物种的其他页面；测试期内不改 compatibility / fish-health 测试页
- 第 5 步：每批 ≤10 页，check + dupes + 审计 ≥95 后才 render，加 sitemap，GSC 观察 2–3 周

## 4. 对照哥飞知识库：可以改的地方

参考资料：`~/Documents/SEO资料库/gefei-seo-cookbook`，主要是《如何给一个已经上线的网站出SEO改造建议》《新站批量化上页面，必死》《新站不批量上页面，那要怎么做页面》《从 TDK 到 TDH》。哥飞改造的大原则：**已有 URL 一律不改**，在此基础上 ① 挖需求加新页面 ② 改老页面（TDK、内链树、sitemap、canonical、H 标签）。

以下问题均于 2026-10-28 线上实测，按优先级排列。

### P0：结构性问题

**1. `/species` 总览页没有列出 8 个新物种页**
- 实测：`/species` 页面里找不到 mudskipper、iridescent-shark、demasoni、golden-orfe 的链接（archer-fish 这种 app 里本来就有的能找到）。
- 哥飞规则：内链是树形，首页 → 子目录 → 内页，内页要能从上级目录点进来。现在这 8 页只能从首页物种区和几个相近物种页的 related 进入，`/species` 这根"枝干"是断的。
- 另外 `/species` 没有 canonical，description 写着"48+ species"，已经过时。
- 改法：在 species app 的总览列表里加上这 8 个 slug（app 仓库 `fishcareai-species-app`）；或者在本仓库为 `/species` 做一个静态覆盖页。前者更干净。

**2. 首页 HTML 里有 11 个 `<h1>`**
- 实测首页源码：除首页自己的 H1 外，还包含 "Aquarium Care Guides & Articles"、"About Us"、"Contact FishCare"、"Betta Fish Care for Beginners" 等其他页面的 H1（SPA 把多个视图都写进了同一个 HTML）。
- 哥飞规则：一个页面只能有一个 H1；首页的主题会被这些混入的内容稀释。
- 改法：首页源码只保留首页视图的内容，其他视图改为按路由加载，或者至少把非首页视图里的 `<h1>` 降成 `<h2>`/`<div>`。改之前先确认这些视图在别的 URL 上是否有独立页面（如 `/about/` 已有）。

**3. compatibility：4,000+ 程序化页面 vs "新站批量上页面必死"**
- 哥飞的判断标准：新站（外链域名 < 100、前 20 名页面 < 100）不应该批量上程序化页面，应该先 10 页、20 页地放量，确认收录和出词后再扩大。
- 这批页面已经上线，按"已有 URL 不改"原则不应删除或改 URL。建议：A/B 测试评估完后，用 GSC 导出 `/compatibility/` 的收录情况，对"已发现未收录 / 已抓取未收录"且没有曝光的鱼对页，考虑 `noindex` 并从 sitemap 移除，让抓取预算集中在有曝光的页面上。这是需要用户拍板的决定，先出数据。

### P1：老页面优化

**4. `/tools/` 不是目录页，而是 meta refresh + JS 跳转**
- 实测：`/tools/` 返回 200，内容只有 `<meta http-equiv="refresh">` 和 `window.location.replace` 跳到 `/tools/aquarium-size-calculator/`，canonical 也指向那里。
- 问题：树形结构里少了"工具"这根枝干；用 200 + 前端跳转也不如 301 清楚。
- 改法：做一个真正的工具目录页，列出 16 个 tools + 14 个 calculators（`/calculators/` 已是目录页，可以合并或互链）；如果暂时不做，至少改成 nginx 301。

**5. app 模板物种页偏薄，并和 `/guides/` 抢词**
- 实测 `/species/neon-tetra`：title 只有 "Neon Tetra Care Guide"，description 是模板句，页面内链只有 6 个。app sitemap 里这种模板页约 258 个。
- 同时 `/guides/` 下多数大众鱼种都有 "X Care Guide" 长文（例如 `/guides/goldfish-care/` 的 title 是 "Goldfish Care Guide: Tank Size, Feeding & Lifespan"）。两个页面都叫 "X Care Guide"，违反"一个关键词一个页面"。
- 已做好的示范：深度页 goldfish、betta-fish、molly 已经把主词换成档案型（"Goldfish Species Profile, Types and …"），避开了 guides。
- 改法：在 app 模板里把 title 改成 "X Species Profile, Size and Tank Setup" 这类档案型叫法，并在页面里加一条指向对应 `/guides/x-care/` 的链接。改的是 app 仓库。

**6. 内页 TDK 格式**
- 哥飞建议内页 title 结构为"内页主要功能 - 子栏目名 - 网站名"。深度物种页现在的 title（如 "Mudskipper Care, Paludarium Setup and Brackish Water"）没有品牌名，fish-health、compatibility 有 "| FishCare AI"。
- 影响不大，标题长度已经卡在 60 字符内。可以在之后的批次里视长度决定是否加 " | FishCare AI"，不必回改已上线页面。

**7. sitemap 的 lastmod 过旧**
- `sitemap.xml` 里 `species/sitemap.xml`、`fish-health/sitemap.xml`、compatibility 都还是 2026-08-24，而 fish-health 有 40 页在 09-28 被重写、species 有 20 页在 10-25 被重写。
- 改法：species / fish-health 的 sitemap 由 app 生成，需要在 app 里让被静态覆盖的 slug 输出真实修改时间；本仓库 `sitemap.xml` 里这两条的 lastmod 也一起更新。

**8. compatibility 面包屑跳过物种子目录**（10-05 全站抓取时的结论，本次未复查）
- 鱼对页的面包屑没有经过物种 hub，首页也不直接链到它。按树形规则应为 首页 → Compatibility → 物种 hub → 鱼对页。测试结束后再改模板。

### P2：放量和外链

**9. 新页面按批放量，并把结果记下来**
- 物种页：已按哥飞方法分批（每批 ≤10），这是对的。缺的是第 0 步的量化数据（KGR 全是 TODO）和 GSC 回看，下一批之前补上。
- 哥飞的目标：手工做到"前 20 名的页面 ≥100 个"，之后才有资格批量。建议每月从 GSC 统计一次"排名前 20 的 URL 数"，作为放量的门槛指标。

**10. 外链**
- 目前主要靠目录站徽章和资源页互链（homepage badge rail、`/resources/`、`/add-your-site/`）。哥飞的看法：nofollow 外链对提升权重也有作用，但要持续做；新站外链域名 < 100 是做中等竞争词的主要瓶颈。
- 建议：外链域名数也作为月度指标；优先拿和鱼类/宠物相关的站点链接（论坛签名、宠物目录、水族博客的资源页）。

## 5. 操作注意事项

- **本地 checkout 不可信**：本地 `main` 落后于 origin 多个提交，并且有很多未提交的改动（`index.html`、`nginx.conf`、`about/`、`privacy/`、若干 species JSON 等）。这些改动很可能是其他会话或同事留下的，**不要 `git add` 进去，也不要从本地推送**。
- **正确做法**：`git worktree add --detach <临时目录> origin/main`，在那个检出里渲染、提交、推送。小改动可以用临时 index（`GIT_INDEX_FILE` + `read-tree origin/main`）直接在 origin 上构造提交。
- **nginx.conf**：经常有别人没提交的改动。提交时只提交生成器重写的那一段（species deep / fish-health deep），不要 `git add nginx.conf` 整个文件。
- **git 很慢**：这个仓库的 git 命令经常超过 2 分钟，放到后台跑。
- **不要重跑的生成器**：`data-pipeline/generate_tank_size_pages.py`（输出已过时，会覆盖手工修正）；compatibility 生成器在测试评估前不要跑。parrot / puffer / snakehead 簇的生成器是同步的，改内容要改生成器再重跑。
- **`/wiki/` 下的文件**：先 grep `nginx.conf` 看这个 slug 是否已 301 到 `/species/`，已跳转的本地文件改了也没用。
- **验证上线**：推送后约 1 分钟，用 `curl "https://www.fishcareai.com/<path>?v=$RANDOM"` 绕过 Cloudflare 缓存确认。
- **on-page 审计**：`python3 ~/.claude/skills/onpage-audit/scripts/onpage_audit.py <html> -k "<主词>" --url <线上 URL>`，目标 ≥95。冒号和主词重复会拉低分数。
